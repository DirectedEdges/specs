Configuration gives you technical control over how specs are created — the same options drive both the Figma plugin and the CLI, so a component produces the same structured output no matter which one generates it.

Two kinds of value exist, whichever surface you set them on:

- **Conventions are facts.** Every consumer reading the same library declares the same
  values, so a wrong value produces *incorrect* output — undetected glyphs, missed
  subcomponents, a concept landing on the wrong prop.
- **Settings are choices.** A different team could set any of them differently and still
  be correct — a different value produces merely *different* output.

Declaring a convention is also what enables its processing: a declared `glyphs` pattern
turns glyph detection on, and an absent block means the library has no such convention.
There is no separate on-switch.

### Format

The **Format** section controls how spec data is serialized once it's extracted:

- [Format](/settings/output-format/) — Serializes specs as `YAML` or `JSON`
- [Keys](/settings/keys/) — Renames keys, such as `camelCase` or `snake_case`
- [Naming](/settings/figma-keys/) — Declares the convention your Figma file uses, keeping renamed keys reversible
- [Tokens](/settings/tokens/) — Serializes as forms such as a name string or `{ $token, $type }` object
- [Color](/settings/color/) — Formats color, such as `#FF6600` or `{ colorSpace, components }`

### Variants

The **Variants** section controls how variant property combinations are compared and included:

- [Variant Depth](/settings/variant-depth/) — Compares depths such as `1` prop at a time or `9999` (all combos)
- [Empty Variants](/settings/empty-variants/) — Includes variants like `{ a:2, b:2 }` with no overrides
- [Invalid Variants](/settings/invalid-variants/) — Includes invalid combos, e.g. `disabled:true, hover:true`
- [Invalid Combinations](/settings/invalid-combinations/) — Summarizes as `invalidPropConfigurations: { disabled:true }`

### Elements

The **Elements** section controls which layers are detected as special-purpose content:

- [Glyphs](/settings/glyph-name-pattern/) — Matches names like `DS Icon Glyph / check`
- [Subcomponents](/settings/subcomponents/) — Matches names like `Card / _ / Header` within `NESTED` or `PAGE`
- [Collapse Primitive Wrapper](/settings/collapse-primitive-wrapper/) — Collapses a wrapper around a lone `text` or `glyph` child
- [Default Slot Content](/settings/default-slot-content/) — Emits authored defaults as `slotContentExamples`
- [Instance Examples](/settings/instance-examples/) — Detects frames like `{C} Example` as `instanceExamples`
- [Images](/settings/images/) — Captures image fills as `backgroundImage` or routes them through an image component

### Props

The **Props** section controls how code-only and inferred props are detected:

- [Code-Only Props](/settings/code-only-props-pattern/) — Detects a layer like `Code only props`
- [Slot Constraints](/settings/slot-constraints/) — Merges `anyOf`, `minChildren`, `maxChildren` into the slot prop
- [Infer Number Props](/settings/infer-number-props/) — Emits `minRows: 2` as `NumberProp` instead of `StringProp`

### Layout

The **Layout** section controls how element hierarchy is represented:

- [Layout](/settings/layout/) — Nests such as `layout:` or flattens as `elements: { parent, children }`

A workspace authors configuration as a `config/` directory, one file per question:

```
config/
├── settings.yaml              What do I want out of this run?
└── conventions/
    ├── figma.yaml             What is true about this Figma library?
    ├── figma.primitives.yaml  Which component does a raw layer stand for?
    ├── specs.yaml             What do the spec's own props mean?
    ├── react.yaml             How does React spell those components?
    └── web-components.yaml    …and Web Components?
```

Every file is optional and defaults independently. `specs init` writes all of them
except the promotion table, each with inline comments.

Conventions are **one file per platform** (ADR-078). The filename is the platform:
`figma.yaml` describes the design tool, `react.yaml` and `web-components.yaml` describe
the code platforms generated from it. `specs.yaml` is a sibling rather than a platform —
the spec is the hub every platform converts to or from. Because a convention describes
the library rather than any one workspace, a library can publish its `conventions/` once
and every consuming workspace adopts it verbatim.

The CLI reads `./config/` in the current directory, or a different directory given to
`--config <path>`. Nothing else is read: a directory counts as configuration if it holds
`settings.yaml` or a `conventions/` directory, and `.json` is accepted everywhere `.yaml`
is. A pre-split `specs.config.yaml` is *detected but never loaded* — finding one is an
error, not a fallback. See [Legacy single file](#legacy-single-file).

## What each file carries

### `config/settings.yaml`

Choices about this run: where data is read from and written to, and the shape of the
spec.

```yaml
author: Your Name

data:
  # Where `specs fetch` writes payloads, and where `generate` loads them from
  directory: ./data
  sources:
    library:
      key: REPLACE_WITH_LIBRARY_FILE_KEY
      fetch: ['file', 'variables', 'styles']
    foundations:
      key: REPLACE_WITH_FOUNDATIONS_FILE_KEY
      fetch: ['variables', 'styles']

spec:
  directory: ./specs
  format: YAML
  keys: SAFE
  layout: LAYOUT
  tokens: TOKEN
  variantDepth: 2
  details: LAYERED
  invalidVariants: false
  invalidCombinations: true
```

### `config/conventions/figma.yaml`

Facts about the Figma library — what its layer names mean.

```yaml
naming: SENTENCE            # the file's layer/property naming convention

glyphs:
  match: 'DS Icon Glyph / {i}'

codeOnlyProps:
  match: 'Code only props'

subcomponents:
  match:
    - '{C} / _ / {S}'
```

### `config/conventions/specs.yaml`

Facts about the spec's own props: which variant props are states, and which props
carry an accessible name or a value.

```yaml
states:
  hover:
    prop: state
    value: hover
  disabled:
    prop: disabled

accessibility:
  label: { prop: a11yLabel }
```

### `config/conventions/react.yaml` and `web-components.yaml`

Facts about each code platform: which of its components a promoted primitive
becomes, and which prop receives styling nothing mapped.

```yaml
stylesProp: sx

primitives:
  text:
    component: DsText
    props:
      content: text
```

### `config/conventions/figma.primitives.yaml`

The promotion table: which design system component a raw layer stands for, and how
its styles become that component's props. Not seeded by `specs init` — a workspace
adds it when it turns [`promotePrimitives`](/settings/promote-primitives/) on.

## Validation

Every configuration value is validated, and an invalid one falls back to its default
with a warning so builds continue:

```bash
$ specs generate data/library.file.json -c Button
Warning: Invalid spec.keys: 'invalid'. Using default: SAFE.
Valid values: SAFE, CAMEL, SNAKE, KEBAB, PASCAL, TRAIN
```

A *misplaced* file is different, and is refused rather than defaulted: a stray
`config/conventions.yaml` (pre-ADR-078) or a `config/conventions/primitives.yaml`
missing its `figma.` qualifier stops the run and names the rename that fixes it.

## Legacy single file

A pre-split `specs.config.yaml` (or `.json`, or `~/.specs/config.yaml`) is no longer
read (ADR-071). When the CLI finds one it stops rather than falling back to defaults —
a defaults-only run would generate specs missing everything your configuration
declares:

```
specs.config.yaml is no longer read (ADR-071).
  Run `specs migrate config` to write config/conventions/ and config/settings.yaml from it.
  Docs: https://specs.directededges.com/settings/
```

Run [`specs migrate config`](/cli/commands/migrate/) once to convert. It writes
`config/settings.yaml` and the `config/conventions/` files, then renames the source to
`specs.config.yaml.migrated` so discovery stops finding it. Review the generated files,
then delete the renamed original. Each option page notes its legacy path.

## Priority

Three levels, highest first. This only matters when the same value is stated in more
than one place:

1. **CLI flags** — explicit overrides for one command
2. **Config files** — the project's defaults
3. **Fallbacks** — convention-based defaults when nothing is configured

A flag always wins:

```bash
# settings.yaml has spec.format: JSON — the flag overrides it to YAML
specs generate data/library.file.json -c Button --format yaml
```

The flags that override a configured value are `--format` (`spec.format`),
`--variables` and `--styles` (the payload paths for that run), and `--config`, which
points at a different directory entirely:

```bash
specs generate data/library.file.json \
  -c "Button" \
  --config ./configs/mobile \
  -o specs/mobile/button.yaml
```

With nothing configured and no flags given, the CLI falls back to conventional
locations — `./data` for payloads, with `variables.json` and `styles.json`
auto-discovered beneath it.

## Keeping configuration in version control

Commit `config/` so the team shares it. The `conventions/` files are worth sharing
further still: they describe the library, not the workspace, so every workspace
reading the same library should carry the same ones — and they are typically identical
across environments, while settings are what differ:

```
project/
├── config/                  # Default (development)
├── configs/production/      # Production
└── configs/staging/         # Staging
```
