`specs-schema` offers a schema for describing components and composition formally and precisely as TypeScript types and JSON Schema. This file serves as a primer to understand the landscape and provide links to explore deeper when necessary.

## `component` and `composition` types

The schema organizes two kinds of spec — **`components`** and **`compositions`** — into a graph. [Components](/schema/component/) are reusable, and arranged inside other components as well as inside [compositions](/schema/composition/) that serve as a page type, template, pattern, or other scaffold. Instances of a component can be nested as an element in another component, composed in another component's slot, or arranged in a composition. When a component is only allowed to be nested inside a another specific component, it's a [subcomponent](/schema/subcomponents/) that's shipped with the parent.

## `api`, `variants` and `examples` files

A spec is written as two or three files: `api`, `variants` and `examples` into a [`components/<component name>/`](/schema/component/) or [`composition/<composition name>/`](/schema/composition/) directory. Other files, such as `styling` produced by an analysis, are not part of the formal spec. What each file holds differs by kind — a composition has no `props`, so it has nothing for a `default`/`variants` layering to be a delta of.

### `api`: "The contract file"

`api` holds the [anatomy](/schema/anatomy/), [props](/schema/props/), and the prop combinations that are invalid

```yaml
props:
  <prop name>:
    type: # boolean, string, slot, ...
    ...
anatomy:
  root:
    type: container
  <element name>:
    type: # text, glyph, container, nested instance, ...
    instanceOf: # reference to another component
invalidPropCombinations:
  ...
```

### `variants`: "The styling and content file"

`variants` holds the default and varying [layout] structures, [styles] and [content].

```yaml
default:
  layout: # nested layout array structure
    - root: # top node is always `root`
      - <element name>:
        - <element name>
      ...
  elements:
    <element name>: # every element gets an entry
      styles:
        width:
        layoutSizingHorizontal:
        backgroundColor:
        ... # style properties vary by element type
      content: # literal or $binding to a prop
      children: # reference to a slot property
      propConfigurations: # for nested instances
variants: # zero or more layer, just like css
  - configurations:
      ... # key/value pairs, like disabled:true
    layout:
      ... # same schema as default, of a complete different tree
    elements:
      ... # same schema as default, for impacted elements only
```

#### Layering

[`Variant layering`](/guides/variant-layering/) works like CSS. The default variant is the complete baseline: every element fully described, with styles, content and layout. Every entry in `variants` is a layered *delta* — a [`configuration`](/schema/prop-configurations/) saying which prop values activate it along with the layout, styles and content that changes because of it. A component's resolved state is all the layered variants merged in order onto the default.

### `examples`

`examples` holds ready-made instances as well as examples of the component's slot(s) (which are actually compositions themselves)

### `api`: identity and structure

`api` holds the composition's [anatomy](/schema/anatomy/), plus the `title` and `description` a component's `api.yaml` has no field for.

```yaml
title: # optional, human-readable label
description: # optional, purpose and usage notes
anatomy:
  root:
    type: container
  <element name>:
    type: # text, glyph, container, nested instance, ...
```

### `variants`: how it looks

`variants` holds `elements` and `layout` — the composition's one, unvarying appearance.

```yaml
elements:
  <element name>: # every element gets an entry
    styles:
      width:
      layoutSizingHorizontal:
      backgroundColor:
      ... # style properties vary by element type
    content: # literal or $binding to a prop
    children: # reference to a slot property
    propConfigurations: # for nested instances
layout: # nested layout array structure
  - root: # top node is always `root`
    - <element name>:
      - <element name>
    ...
```

A composition does not vary by prop configuration — it has no props — so there is no `default`/`variants` split here the way a component has one. `elements` and `layout` are the whole of it.

### `examples`

`examples` holds the composition's named `slotContent` fills — content bundled alongside the primary content, each one its own `anatomy`+`elements`+`layout` triplet.

### `styles` and content

Styles and content work the same way for an element in either kind — `Elements` is the same type whether it belongs to a component's `default`/`variants` or a composition's flat `elements`.

[Styles] are organized per [element] and take different shapes:

- **Flat and wide** — dozens like `width`, `layoutSizingHorizontal`, `textColor` and `backgroundColor`.
- **Deep** — [`typography`](/schema/typography/) gathers the text properties under one node that corresponds to a text style, while [`effects`](/schema/effects/) and [`GradientValue`](/schema/gradient-value/) also have deep, sophisticated shapes.
- **Side- and corner-shaped** — `padding` and `strokeWeight` as [`Sides`](/schema/sides/); `cornerRadius` is [`Corners`](/schema/corners/) that can be single value or several addressable parts (like `{ start:, end:, top:, bottom: }`).

Style values can be a literal, a [`TokenReference`](/schema/token-reference/), a [`PropBinding`](/schema/prop-binding/), or a [`Conditional`](/schema/conditional/). A composite token can be bound to `typography` and `effects` (Figma's text and effect styles, respectively).

Content surfaces directly through primitives as well as nested components that wrap primitives in an API. Content is mostly two things: [text] strings and [glyph] by name, reaching an element through `content` as a literal or a `$binding` to a prop. Image content flows through as both `backgroundImage` properties on elements and source properties on components. References to image files are declared in `examples.yaml`.

All three content types — and the containers that scaffold layout — are frequently offered as components themselves too. An `Icon` component that wraps a glyph element (the simple vector) with props for size and color; a text primitive element or a `Text` component with props for style, size and color.

## Composing Layouts and Slots

Layout is a tree, and there is one per component, per composition, and per instance. [`layout`](/schema/layout/) in a variant is where it lives.

Slots are what make those trees combine. A slot is a prop a component exposes for content it does not define, and a fill arrives one of two ways:

- **Into a default slot** — an instance filling a component's designated default slot is nested as a plain [child](/schema/children/). **The nesting is the fill**, and nothing points from one level to the next.
- **Into a named slot** — every other fill binds explicitly through a [`SlotContentRef`](/schema/slot-content-ref/) into [`slotContentExamples`](/schema/slot-content/), which is the only shape that can say *which* of several slots a fill belongs to.

Both appear in one spec, so both have to be read. Because many slots are default slots, their fills merge into **consolidated layout trees** — a composition's tree is not the concatenation of its components' trees but the result of those fills resolving into place.

**Following a slot crosses all three files.** The slot prop is declared in `api.yaml`, its example content lives in `examples.yaml`, and the binding that places it is in `variants.yaml`. That traversal is the part of the schema most worth understanding before reading a catalogue, because no single file shows it.

## References

A spec points at things rather than repeating them, with five references. Each is stored as a value in one file and resolved somewhere else — so these are the paths to follow when reading a catalogue. `<property>` in the Found in column is most often `children`, `content`, `visible` or `value`.

| Reference | Found in | Value |
|---|---|---|
| `instanceOf` | `api.yaml` at `anatomy.<element>.instanceOf` | A component key, as a plain string |
| [`$ref`](/schema/subcomponents/) | `api.yaml` and `variants.yaml` at `anatomy.<element>.instanceOf` | `"#/subcomponents/<name>"` |
| [`$binding`](/schema/prop-binding/) | `variants.yaml` at `default.elements.<element>.<property>`, and the same path under each entry of `variants` | `"#/props/<prop>"` |
| [`$slotContent`](/schema/slot-content-ref/) | `variants.yaml` at `...elements.<element>.examples` | `"#/components/<component>/slotContentExamples/<name>"` |
| [`$slotContent`](/schema/slot-content-ref/) | `examples.yaml` at `instanceExamples.<name>.propConfigurations.<slotProp>` | `"#/components/<component>/slotContentExamples/<name>"` |
| [`$token`](/schema/token-reference/) | `...elements.<element>.styles.<property>` | A token name, alongside a `$type` |

## Conventions

[Conventions](/schema/conventions/) change the *shape* of the spec, not its formatting — the same Figma file produces different specs under different conventions. For a schema reader, the question each convention answers is which part of the spec looks different, not what a convention is in general (see [Settings](/schema/settings/) for that distinction):

| Convention | What it changes |
|---|---|
| [`glyphs`](/settings/glyphs/) | whether a component is typed `glyph` with a resolved name, or an ordinary element |
| [`subcomponents`](/settings/subcomponents/) | whether one component becomes a parent with nested subcomponents, or stays flat |
| [`codeOnlyProps`](/settings/code-only-props-pattern/) | whether a prop reaches the spec at all |
| [`naming`](/settings/figma-keys/) | whether a key can be reversed back to its original layer name |
| [`states`](/settings/states/) | whether a variant prop emits a CSS pseudo-class or a `data-*` attribute |

`DEFAULT_CONVENTIONS` is an empty object, and that is deliberate: a default can supply a missing *member* of a declared convention, but never a convention block — their absence is a statement about the library, and inventing one would fabricate a fact nobody declared. The full per-platform treatment is at [Conventions](/schema/conventions/).

## Package Exports

The package exports TypeScript types for every node in the schema, plus two runtime values:

```ts
import type { Component } from '@directededges/specs-schema';
import { DEFAULT_SETTINGS, DEFAULT_PIPELINE } from '@directededges/specs-schema';
```

`DEFAULT_SETTINGS` and `DEFAULT_PIPELINE` are the only runtime exports. All other exports are type-only. There is no defaults export for [Conventions](/schema/conventions/): a convention's absence means the library declares no such convention, and nothing can supply that.

## Analysis reports

The schema affords analysis because it's a declared graph, not loose prose — typed props, styled elements, and `instanceOf`/`$binding`/`$token` references that resolve the same way everywhere. [`specs analyze`](/cli/analyze/) walks that graph catalogue-wide and writes the result into `analysis/`, answering questions no single spec can, such as which components share a prop (`props.yaml`) or a change's blast radius before it's made (`dependencies.graph.yaml`). The full report list and what each one summarizes is at [Analyze](/cli/analyze/).
